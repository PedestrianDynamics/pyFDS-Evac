      Movement models

      Movement models

      Note

      This page covers the JuPedSim operational model that moves the agents: which models a deck can select, the values pyFDS-Evac passes to each, and how each one behaves when agents meet in a door or head-on. The models themselves are described on JuPedSim’s model pages.

      A deck selects its movement model with simulationParams.model_type (Scenario JSON › Simulation settings). The default is CollisionFreeSpeedModel. Smoke, gas dose and routing act on top of the movement model and are the same for every choice.

      Choosing a model

      No supported model passes all three test cases below, so the default stays CollisionFreeSpeedModel.

      • Unidirectional egress (everyone heading out, doors and corridors): use CollisionFreeSpeedModel. Accept that a crowd can jam in a narrow opening, check that every run completes before you read an evacuation time, and run several seeds.
      • Dense head-on counterflow: SocialForceModel clears the 50 % case below (Iso-06-counterflow-50, 3 seeds; pushing not validated against measured counterflow). Agents then reach about 2.2 times their desired speed, and the friction is 0 (#635). Report both with any result. The 100 % case and WarpDriverModel are in Counterflow with hard journeys.
      • Not recommended: AnticipationVelocityModel (#758), GeneralizedCentrifugalForceModel, and WarpDriverModel, which completes some runs only by letting agents overlap.

      A run whose whole crowd stands still for 100 s stops with end_reason "deadlock" and reports the stuck agents (#760); the jam itself is not cleared.

      Deadlock behaviour

      Test cases

      Important

      Scope. A study of three cases in clear air, at main 47cfeec5 with JuPedSim 1.4.2. Every model ran with pyFDS-Evac’s mapping below, with only model_type changed, except CollisionFreeSpeedModelV2, which needed strength_neighbor_repulsion 2.6 and range_neighbor_repulsion 0.1 in the deck (#757). Values that pyFDS-Evac does not set keep JuPedSim’s defaults. A run is a deadlock when it is incomplete and at least two of its agents moved less than 0.03 m over the last 100 s. A run overlaps when its closest pair of agents comes within 0.9 × 2r, centre to centre. These are implementation checks on three geometries. They do not validate any model against measured crowd movement, and the rates have not been shown to hold for other geometries, densities or seeds.

      CollisionFreeSpeedModel. Agents stop at contact: the smallest distance between two centres is 1.00 × 2r, and between a centre and a wall about one radius. There is no side-step and no push, so a pair that meets face to face waits for the rest of the run. On HUT at r = 0.15 m, 5 of 13 seeds jam; which seeds jam changes between commits (#706). On the 50 % counterflow the two streams lock, with one agent out in seed 1 and none in seeds 2 and 3 (#745). The familiarity deck completes every run (#359).

      CollisionFreeSpeedModelV2. With the repulsion values of CollisionFreeSpeedModel supplied in the deck, it gives the same numbers on every case. A deck that omits strength_neighbor_repulsion or range_neighbor_repulsion, which covers every deck imported with pyfds-evac init and every jupedsim-web-community deck, gets the CollisionFreeSpeedModel value 2.6 or 0.1 m for each missing key (#757).

      SocialForceModel. It clears the 50 % counterflow in all 3 seeds (mean 86 s) by pushing. With hard journeys it clears both counterflow cases (below). The peak speed is 2.65 m/s at a desired speed of 1.2 m/s, about 2.2 times the desired speed, and 2.41 m/s on Familiarity 20. The friction is 0 in every run (#635). On HUT, 4 of 13 runs complete. One meets the deadlock criterion. In the other 8 a single agent is left, standing still just south of the 0.75 m gap at the same spot in every seed; the cause is not established. The familiarity deck uses this model, and its doorway deadlocks are those of #359: 3 of 150 and 7 of 60 runs.

      AnticipationVelocityModel. Not recommended (#758). Its model-level parameters are commented out in the mapping, so the model runs at JuPedSim’s defaults. pyFDS-Evac never sets its rng_seed, and JuPedSim draws a new one each time it is imported, so a run cannot be reproduced from the run seed. Agent centres come within 0.03–0.18 r of walls.

      GeneralizedCentrifugalForceModel. Not recommended. It refuses most spawns and overlaps when it runs. It fails at spawn on HUT and the counterflow deck in every seed, with “too close to geometry boundaries” on HUT and “outside of accessible area” on the counterflow. On Familiarity 5 the 4 runs made complete, and 3 of them overlap, with two centres as close as 0.12 × 2r.

      WarpDriverModel. It completes every run, some only by letting agents overlap: 3 of 13 HUT runs (centres as close as 0.41 × 2r), all 3 counterflow runs (0.67 × 2r) and 1 of 60 Familiarity 20 runs (0.35 × 2r); on every case agent centres come closer than half a radius to a wall in some runs. station_fahy uses this model; its choice is under review in #761.

      CollisionFreeSpeedModelV3 is in JuPedSim 1.4.2 and is not offered by pyFDS-Evac (#759). A deck that names it stops with a ValueError.

      At run time. pyfds_evac/core/deadlock.py applies the study’s definition during a run: the thresholds are the same, 0.03 m of net displacement over 100 s. The run-time rule is stricter: it needs every counted agent to be still, not “at least two”, so a working bottleneck with a few agents creeping through never fires it. It also holds back while any agent is held by design (pre-movement, a waiting stage, a desired speed of 0, a flow source that can still spawn, an exit yet to open), and it stops the run while it is under way instead of judging the end state. The counts of runs that end deadlock are therefore not comparable with the study’s counts. The run then stops with end_reason "deadlock"; pyFDS-Evac reports the jam and does not clear it. See Reading the results.

      Counterflow with hard journeys

      Since #504 the counterflow decks keep their counterflow only with their two journeys, each given a transition {"from": <distribution>, "to": <exit>, "journey_id": <journey>} and "allocation": "hard". The decks are Iso-06-counterflow-50 (150 agents) and -100 (200 agents) of jupedsim-web-community (82404ee), clear air, radius 0.15 m, desired speed 1.2 m/s, seeds 1–3, run at 7689907e (#745). The closest pair is the smallest centre distance over all frames, in units of 2r; the peak speed is the largest frame-to-frame speed of any agent.

      Coded mapping

      The model is built by _MODEL_BUILDERS (scenario.py), and each agent’s parameters by create_agent_parameters (simulation_init.py). Every model receives the agent’s radius and v0 from its spawn area, 0.2 m and 1.25 m/s when the deck sets neither, except GeneralizedCentrifugalForceModel, which receives no radius.

      Values passed to each model

      Keys are those of simulationParams in config.json. “JuPedSim” marks a value that pyFDS-Evac does not pass, so JuPedSim 1.4.2’s default applies.

      CollisionFreeSpeedModelV2: the repulsion values are per agent. strength_neighbor_repulsion and range_neighbor_repulsion are read from the deck. Each missing key takes the CollisionFreeSpeedModel value: 2.6 for the strength (JuPedSim’s is 8.0) and 0.1 m for the range (#757). time_gap is fixed at 1.0 s; the wall repulsion keeps JuPedSim’s 5.0 and 0.02 m.

      SocialForceModel

      JuPedSim parameter (deck key)Value
      body_force (sfm_body_force)120000

      A deck that sets sfm_friction above 0 gets a warning, and the run manifest records the requested and the applied friction.

      AnticipationVelocityModel: no model-level value is passed, so pushout_strength is JuPedSim’s 0.3 and rng_seed is drawn at import (#758). Per agent, anticipation_time (1.0 s) and reaction_time (0.3 s) come from the deck keys of the same name, defaulting to JuPedSim’s values; the CollisionFreeSpeedModel keys T and s0 are not read (#868). time_gap is fixed at 1.06 s, and the neighbour repulsion keeps JuPedSim’s 8.0.

      GeneralizedCentrifugalForceModel: the model takes gcfm_strength_neighbor_repulsion (0.3), gcfm_strength_geometry_repulsion (0.2), gcfm_max_neighbor_interaction_distance and gcfm_max_geometry_interaction_distance (2.0 m), gcfm_max_neighbor_repulsion_force (9.0) and gcfm_max_geometry_repulsion_force (3.0). Per agent it takes the deck keys mass (1, JuPedSim’s default), tau (0.5 s), a_v (1.0), a_min (0.2 m), b_min (0.2 m) and b_max (0.4 m). The deck’s radius is not passed; the body size comes from a_min, b_min and b_max. JuPedSim 1.4.2 multiplies the driving and neighbour forces by mass and divides their sum by it, but leaves the wall force unscaled, so a mass above 1 weakens only the walls (#868). Decks exported from the JuPedSim web app carry "mass": 80.

      WarpDriverModel: time_horizon (2.0 s), step_size (0.5 s), sigma (0.3), time_uncertainty (0.5), velocity_uncertainty_x and velocity_uncertainty_y (0.2), each under the same deck key. All equal JuPedSim’s defaults.

      Limitations

      • The deadlock rates above come from three geometries and a few seeds each. A smaller radius does not remove the CollisionFreeSpeedModel jam: HUT at 0.15 m still jams in 5 of 13 seeds.
      • SocialForceModel pushing has not been validated against measured counterflow. On the counterflow case its peak speed exceeds the desired speed by a factor of about 2 (Counterflow with hard journeys).
      • pyFDS-Evac has no counterflow algorithm of its own (Model comparison › Movement model).
      • The open defects are listed under Limitations › Known defects.
